## Scenario

`scripts/live-vera-regression.sh` (`npm run test:live:vera`) keeps the #241
seed → upgrade-store → run → restart shape and adds a second `VeraFlows`
workspace. The existing seed/run/restart phases and their assertions are
unchanged; the run phase's durability counts are scoped to `VeraProbe` because
the new workspace shares the roster.

The flows phase drives real terminal review/synthesis turns and real
`ensemble_dispatch` tool calls through the isolated host. A normal native
kickoff is not a terminal turn, so each first dispatch is seeded by a worker
completion review (the terminal continuation path) rather than by a kickoff
tool call:

1. **Five-hop relay.** A native leader turn starts a leader-owned command root
   with one worker. The worker relays to five named siblings through `$Name`
   final-text routing. Every intermediate parent relays; the command root is the
   only synthesis task. The terminal synthesis mentions two workers; those
   mentions are references, so no peer turns are created.
2. **Multi-ticket continuation.** The relay root's terminal turn calls
   `ensemble_dispatch` with a five-way ticket-two assignment batch. Ticket two
   is a new parentless leader-owned command root with a fresh group/command
   budget (`5/8` group hops, `5/24` command hops). It gets exactly one
   synthesis. Its terminal turn mentions all five workers, creates no peer
   turns, and posts the visible no-work notice.
3. **Refused dispatch above the new command ceiling.** With command hops
   pinned to `8`, the next ticket's terminal turn calls `ensemble_dispatch`
   with nine assignments. The command-layer preflight refuses it (`9/8`) as a
   batch-too-large command, the refusal tells the leader to reduce or split the
   batch (not to ask for a new command), no task is created, and the terminal
   notice is posted.
4. **Worker route.** A leader-owned command root assigns one worker whose final
   text names a sibling. The peer turn is created and replies; the root still
   gets exactly one synthesis.

Every command root is leader-owned, so the #247 ancestor guard skips every
worker completion. The driver asserts the task graph, leader turn counts,
leader-authored message counts, terminal suppressions, terminal notices, the
dispatch ledger, and the refusal. The fake provider emits the `ensemble_dispatch`
tool call once from the review/synthesis marker, then streams the deterministic
reply after the tool result (the summary for a synthesis turn, the start line
for a normal turn).

## Bug found and fixed

The live flow exposed two real issues in the root-synthesis path. Both fixes are
narrow and covered by tests.

1. **Early root synthesis over a pending descendant.** A replied peer turn can
   route a new `$Name` turn after it settles. `maybeSynthesize` checked only the
   direct children of a parent, so an intermediate parent whose child had just
   routed a pending grandchild could relay upward and promote the root
   synthesis before the grandchild finished. The live relay reproduced this at
   hop two. `branch-digest.ts` now exposes `pendingDescendantResolver` (and the
   `hasPendingDescendant` wrapper); `maybeSynthesize` and
   `reconcileWaitingWork` wait for the whole non-completion subtree. A replied
   intermediate parent also propagates a new child completion to its ancestor
   instead of returning early. The memoized resolver keeps the 5k-task
   reconciliation inside its latency budget.
2. **Synthesis context on a reused leader session.** The leader's workspace
   session first ran the native kickoff turn. The host kept that first
   instruction snapshot for later prompts, so the first synthesis request still
   carried the native turn's recent-transcript context and not the root request
   or branch digest, even though the instruction entry was updated. The run
   path now appends the bounded synthesis context to the synthesis prompt text
   as well as writing it as the context entry. The live provider request records
   both `hasRootRequest` and `hasBranchResults` true for every synthesis turn.

## Review-fix pass

- `ensemble_dispatch` is terminal-turn-only. The Vera flows seed each first
  ticket with a worker completion review (a real terminal turn) instead of a
  normal native kickoff, so the live proof exercises the same boundary.
- The command-cap live refusal is now the batch-too-large copy: reduce or split
  the batch, not a request for a fresh user command.
- The restart checks scope completion turns to the ticket command groups; the
  seed completion reviews are intentional and live in their own groups.
- The subagent probe is pinned to the explicit legacy path. Its one-task and
  barrier assertions predate native-first default-on, where the host mints a
  synthetic native turn for the subagent completion; native ingestion is
  covered by its own suites.

terminal continuation. Per ticket, the post-work leader turn count is one
synthesis. There are no per-hop leader messages and no per-child completion
reviews. Per-ticket token values are rounded up; the total
uses the total character count (`ceil(957/4) = 240`).

## Privacy

The committed record contains fixture names, stored roster titles/roles, task
and group counts, lengths, versions, and token estimates only. It contains no
prompt or answer text, conversation transcript, credentials, file bytes, or
absolute private paths. The live script gates the driver outputs for the
harness root, project directories, password, and every #251 marker family, and
gates the service logs for the same markers and home paths. The relay marker is
kept out of the first 80 characters of the peer-turn text because the service
logs a peer-turn title.
