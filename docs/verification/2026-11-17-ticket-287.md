# Live TUI readiness after opening Ensemble

Ticket [#287](https://github.com/heyimteee/ensemble/issues/287). This record
covers the OpenCode 2.3.0 compatibility failure at the first TUI typing step
and the harness changes that make opening the page and editing the command
line deterministic.

## Environment

| Item | Value |
|---|---|
| Base | `a0c39c0` (`ticket/287-tui-ready`) |
| Platform | Linux/tmux 3.5a |
| Node | 26.12.1 |
| OpenCode | 2.3.0 and 2.2.7 |
| Isolation | `scripts/lib/live-harness.sh`; fresh HOME/XDG roots, project, workspace, fake provider, and host per run |

## Changes

- `live_open_ensemble` now resizes the TUI window to
  `ENSEMBLE_LIVE_TUI_WIDTH`/`ENSEMBLE_LIVE_TUI_HEIGHT` (default 160x60) after
  the `ENSEMBLE` header appears, forcing a redraw and tolerating a missing
  window. It then waits for a non-empty `live_status_line` mode chip before
  returning, so a header-only first paint cannot accept input.
- `src/v2/live-matrix.test.ts` guards the readiness contract with a stubbed
  TUI: a header-only pane fails, a mode word inside another row does not
  satisfy the gate, a real `NORMAL │ Agents` row passes, and the resize is
  issued at the configured geometry.
- The command-line editing step in `scripts/live-check-fake.sh` now waits for
  `:settings` to disappear after Backspace before retyping the single `s`.
  `:setting` is a prefix of `:settings`, so the old wait could pass on the
  pre-Backspace frame; the following retype then restored the exact pane the
  liveness check captured, and `live_type` reported a lost key that had
  actually arrived. Assertions are unchanged in strength; the ordering is now
  unambiguous.

## Limitations

- The CI failure was not reproducible locally: the same 2.3.0 fake suite
  already passed before this change, including the full walkthrough. The
  compatibility job needs a rerun to confirm the fix on the failing host.
- The uploaded CI pane shows the statusline and command line present at the
  failure and the expected `:settings` value in the buffer. That is consistent
  with the retype identity race above, not a lost input surface; the readiness
  gate is the ticket's requested hardening and remains exercised by the guard
  test.
- Linux/tmux only. No macOS, screenshot, or pointer-input evidence.
