## Schema / state-derivation decisions

- **Extended the subtask schema in place** (`queueKey`, `workKind`, `claimedBy`, `leaseUntil`, `deadlineAt`, `retryAfter`, `finishedAt`, `stoppedAt`) instead of a parallel work-item table: one source of truth, no join or drift, sync/load/recovery reuse the existing store machinery, and v5.2 board/TUI readers keep working (stored `state` is a write-through cache; `deriveWorkStatus` is canonical and overlaid as `status` on snapshot subtasks for ticket #56).
- **Dedupe scope:** idempotency suppresses only in-flight duplication (same key, non-terminal row). Finished rows do not block new work — re-asking completed work is legitimate new work. Handoff registrations dedupe including terminal rows (registration is the effect; re-registering posts nothing twice). Delegation keys scope to the delegating turn (`parentID` in the key); handoff keys exclude it so registration stays idempotent across turns while still recording the caller run as correlation.
- **Adaptations from OpenBot mechanics** (documented in `queue.ts`): 5 attempts, 60s lease, ~20s heartbeat, 5-minute deadline, 24h finished retention — taken unchanged; delegation uses the same 5-minute deadline. No cross-replica sweep or 2s poll loop (single-process service): stale leases are reaped on every schedule pass and on snapshot/diagnostic reads (the TUI polls every 250ms), which bounds reap latency without spawning runs from a read path. Transient run exceptions retry with 5s/60s backoff inside budget and deadline; model-availability failures keep the existing user-mediated interrupted-approval path. Handoff hops and agent-to-agent turns reuse the same record/key/derivation foundation; ticket #55 extends handoff caps on top of it.
- **GLOSSARY untouched:** the visible-state vocabulary (`pending/working/replied` plus derived `retrying/failed/cancelled`) is surfaced by ticket #56's work-row UI, which owns the language update if needed.

## Root cause

`src/v2/tui/app.tsx`: the `staggeringIds` memo (then line 367) called `motionOn()`, but `const motionOn = …` was declared ~840 lines below (then line 1210). Solid evaluates `createMemo` callbacks eagerly at creation, so the call hit the `const` temporal dead zone during component setup. `tsc` cannot catch this (use-inside-a-callback before the `const` declaration is legal TypeScript), and no unit test mounts the app component, so `npm run check` and `npm test` stayed green while every live scenario failed at page open.

## Audit of the other v5.4 memos

All 34 `createMemo` call sites in `app.tsx` were audited for the same eager-evaluation-before-`const` pattern. No other genuine hazard exists: `pendingApprovalIDs` reads `pendingApprovals` declared above it; no memo reads `liveMessages`, `liveActivity`, or `motionFrame` before their declarations; the late `pickerItems` memo reads only the `picker` signal and imported helpers. The audit is pinned mechanically (see below), not just by review.

## The fix

- Moved the `staggeringIds` memo below the `motionOn` definition (no behavior change — same inputs, same memo), with a comment documenting the ordering requirement.
- Added `src/v2/tui/app-order.test.ts`: a static declaration-order guard asserting every component-local identifier called inside a `createMemo` body is declared above that memo. Verified both ways — it fails on the pre-fix tree with exactly `memo 'staggeringIds' (line 367) calls 'motionOn' declared below it (line 1210)` and passes post-fix.
- Full app/route mount in the unit harness remains infeasible (the component requires the live OpenTUI plugin host: renderer, router, keymap, storage). The static guard plus the three live scenarios (which all open the real Ensemble page) are the coverage; no comment-only mitigation was used.
