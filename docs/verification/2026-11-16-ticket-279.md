## Scope

This record proves `@heyimteee/ensemble@0.1.0-rc.2` as a built package: the
server, TUI, and RPC entries are compiled JavaScript, the TUI is compiled with
the Solid OpenTUI transform, the TUI runtime packages are declared
dependencies, and the installed package loads through `opencode plugin add`
into an isolated OpenCode 2.2.7 host. No public npm publish, real credential,
workspace link, or repository plugin path is used. The OpenCode configuration,
HOME, XDG directories, project, and mock agent are temporary and were not the
user's global configuration.

## Build shape

`npm run build` runs `scripts/build.mjs`. It compiles the runtime closure from
`src/v2` into `dist` and emits three public entries:

| Export | Built file |
|---|---|
| `.` | `dist/server.js` |
| `./tui` | `dist/tui/index.js` |
| `./rpc` | `dist/rpc.js` |

- `.tsx` files are compiled by `babel-preset-solid` with
  `moduleName: "@opentui/solid"` and `generate: "universal"`, so the installed
  package is Solid-compiled JavaScript rather than runtime `jsx()` calls.
- `.ts` files are compiled by `@babel/preset-typescript`.
- Relative `.ts`/`.tsx` imports are rewritten to `.js` for Node's resolver.
- The build emits 121 JavaScript files: exactly the runtime closure, with
  tests, fixtures, docs, scripts, and the nine development-only modules
  excluded.
- The installed package needs no repository `tsconfig.json`; all JSX handling
  happens before packing.

`npm run check:build` typechecks the runtime closure with
`tsconfig.build.json` and runs `scripts/check-build.mjs`, which rejects a
missing export target, raw TypeScript, a `.ts` import, a `react` reference, or
a TUI entry without the Solid runtime. `prepack` runs the build and this check,
so `npm pack`/`npm publish` cannot produce a tarball without the built entries.

## Runtime dependency choice

The TUI runtime packages are regular, exact dependencies:

```json
"dependencies": {
  "@opentui/core": "0.7.0",
  "@opentui/solid": "0.7.0",
  "solid-js": "1.9.12"
}
```

`@opencode/plugin` stays the host-supplied optional peer with the unchanged
range `2.2.6 || 2.2.7`; the Node floor stays `>=22.23.4`. The isolated install
check resolves all three TUI packages from the plugin cache:

```text
live: PASS installed package: dist/tui/index.js and declared TUI dependencies resolve in the plugin cache
```

OpenCode's runtime plugin support also rewrites the plugin's `@opentui/*`,
`solid-js`, and `@opencode/plugin/tui` imports to its own loaded modules. The
declared dependencies make the package self-sufficient in the cache without
relying on that rewrite; the rewrite is why the same built artifact renders
consistently with the host's OpenTUI renderer.

## Why the build changed shape

The `0.1.0-rc.1` source package failed in two stages, both recorded in the
[#270 record](2026-11-16-ticket-270.md):

1. The installed TSX had no repository `tsconfig.json`, so the host loader used
   the classic JSX runtime and asked for `react`.
2. Adding `@jsxImportSource @opentui/solid` moved the error to a missing
   `@opentui/solid`; the optional peers were not in the plugin cache.

A first built attempt with TypeScript's `react-jsx`/`@opentui/solid`
`jsxImportSource` produced runtime `jsx()` calls. The plugin loaded but the
`/ensemble` page rendered blank, because OpenTUI's Solid transform explicitly
skips `node_modules` and TypeScript does not apply the Solid compile-time
transform. The shipped build therefore uses `babel-preset-solid` and
`generate: "universal"`, and the install check proves the actual rendered
route, not only a successful module evaluation.
