Debugging those tests exposed two real truths worth recording: (1) the
single-hop quiet-window defer must re-`schedule()` after consolidating, or
a lone completion sits past its `retryAfter` with nobody pumping the queue;
(2) synthesis reassigns the finished turn to the leader, so completion
tests match turns by title/kind instead of the original assignee.

## Behavior notes

- Mandatory handoff fires on success finalizes for non-leader assignees
  that are neither completion nor batch hops and have no explicit handoff
  child; the hop carries the finished reply, is keyed
  `completion:<workspace>:<finishedTask>:<recipient>`, parks inside the
  ~1 s batch quiet window (`retryAfter`), posts `Handed to $Leader`, and
  the finisher finalizes immediately (the hop is a post-turn delivery, not a
  wait — only explicit children hold `awaitingChildren`, so a grouped
  completion can never wedge its finisher).
- Batch consolidation parents ≥2 pending completions into one review turn
  (`completion` + `batch`, `itemIDs`), extends the open batch on later
  arrivals, excludes grouped items from the pump while the batch is open,
  and `maybeSynthesize` never auto-closes a batch parent — closure is only
  via `ensemble_review` with every item decided. Leaders end the batch;
  non-leaders hand it onward (default leader) under the same loop guards.
- `delegate` inside review stays leader-only, so mandatory handoff never
  becomes delegate-after-handoff by another name; no duplicate work is
  queued (per-item refusals leave items undecided and the batch open).
- Copy follows `$Name`/`!Name` for agents and `@` file-only everywhere
  (batch listings, refusal and closure notices, `AGENTS.md`, runtime
  identity, `init-block.ts` contract + Tools table + new `End-of-turn
  handoff` section).
- Compatibility: #67 bubbles/completions, #68 approval trust (native rows
  still settle only via host/user), #69 settings, #70 activity states and
  handoff waiting, queue semantics, DMs, wizards/dialogs untouched — six
  existing tests were updated to the new contract by filtering
  `handoff.completion` out of explicit-hop counts and pinning the new hop
  where relevant (`handoff-service`, `handoff-waiting`, `peer-turn-service`,
  `service` outside-roster + restart-recovery).

## Uncertainty

- Live runs were recorded against host 2.2.5 while typechecking against
  2.2.1 declarations; no new host APIs are used (text anchors only), but
  declaration parity is not runtime proof — see the runtime guide.
- The ~1 s batch window is a heuristic: parallel live turns land well
  inside it (one joint fan-out message creates both turns atomically), but
  completions seconds apart stay single direct hops by design.
- Batch review presentation parks in `awaitingChildren` like any parent
  with live children; the TUI renders the generic `Waiting for $Name…` wait
  rather than a batch-specific verb.
