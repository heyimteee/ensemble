## Reproduction evidence (red → green)

`src/v2/tui/activity-state.test.ts` was written first against the old
behavior and failed as required: `activityStateForTask` did not exist, and
the old `activityDetailForTask` derived every non-turn/handoff task —
including approval-gated work, parents awaiting children, and retrying
backoff — as the generic `checking the details…` working line. After the
fix the same file passes 8/8: approval-gated and native-blocked work derive
as `waiting for you…` (`waiting` kind), a parent awaiting children derives
as `Waiting for $Child…`, retrying work names `retrying…`, entries older
than `ACTIVITY_STALE_AFTER_MS` (120s) read stale, and copy follows the
`$Name` grammar with no `@` addressing.

Service-level hang proof is `src/v2/handoff-waiting.test.ts`:
`parentless handoff anchors to the sender's newest open task` pins the
orphan-hop hole (a handoff issued from a session with no live run parents
its hop on the sender's newest open task instead of `undefined`).
`sender waits on the handoff with a visible wait and no double-queue` pins
the contract end to end (parent holds `awaitingChildren` with
`Waiting for $Sage…` while the hop is in flight; a peer `ensemble_delegate`
after the handoff is refused leader-only; exactly one hop row and one
correlation-linked relay land). Debugging that test exposed a real
scheduling truth worth recording: with equal 2000 ms waits the parent tail
and the hop reply race, so the test staggers waits (sender 500 ms, hop
4000 ms) to make the hold deterministically observable — the mechanism
(parent tail reads a fresh snapshot, `children.length > 0` holds
`awaitingChildren`, `maybeSynthesize` completes after delivery) was verified
in a throwaway trace, not assumed.

## What changed

Pure activity seam (`src/v2/tui/workrows.ts`): new `waitingForLine`
(`Waiting for $Name…`), `waitingForYouLine` (`waiting for you…`),
`workingLine` (`working…`, detail when available), `retryingLine`, new
`working`/`retrying` verb kinds with frame routing (working spins,
retrying breathes calm), `activityStateForTask` (needs-you first, then
waiting-for-children, then retrying, then asking for hops/turns, then
`working…`; the generic default is reserved for genuinely unknown
activity), `isActivityTaskStale` (claimed but lease lapsed) and
`isActivityStale` (streaming row older than the bound), and
`splitActivityGroups` now threads `pendingApprovalIDs`/`nativeBlockedIDs`/
`agentNameFor` and hides stale claims from the live surface (WORK rows
still list them, so nothing silently drops). `activityDetailForTask` is
kept for existing callers.

`src/v2/tui/app.tsx`: the group live-activity memo passes the approval and
native-blocked sets plus the agent-name resolver into
`splitActivityGroups`, and filters leaked streaming rows older than the
staleness bound before they can wedge an activity line.

Handoff contract (`src/v2/service.ts`, `src/v2/handoff.ts`,
`src/v2/init-block.ts`): new exported `newestOpenSenderTaskID` pure helper;
`toolHandoff` anchors runless hops to the sender's newest open task
(depth and per-run caps follow the anchor), and the tool result, ack, and
duplicate copy state the wait (`Your turn stays open until the answer

the init-block addressing line, Tools-table rows, handoff steps, the
identity prompt, and the mention-normalized system line now say leaders
delegate while peers hand off (which already queues the hop). No

`live_require_all_text` bounded settle poll; the rich-markdown block

## Uncertainty

- Staleness bound (120 s) is a product choice, not a measured heartbeat
  gap: the lease/heartbeat machinery (60 s / ~20 s) is the liveness signal
  for task-backed lines, the age bound only guards leaked streaming rows.
  A slower host render could in principle need longer than the 20 s
  rich-markdown settle window; the window matches `LIVE_STEP_TIMEOUT`
  convention and passed repeatedly here, but it is a timeout, not a proof.
- The runless-hop anchor picks the sender's *newest* open task as a
  heuristic; a sender with two unrelated open tasks could anchor to the
  wrong one. The alternative (refusing runless handoffs) was rejected as
  a bigger behavior change; the hop still runs exactly once either way.
- Live runs were recorded against host 2.2.5 while typechecking against
  2.2.1 declarations; no new host APIs are used (text anchors only), but
  per the runtime guide this is tested behavior, not a compatibility proof.
