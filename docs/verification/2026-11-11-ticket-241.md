## Scenario

`scripts/live-vera-regression.sh` (`npm run test:live:vera`) runs one isolated
fake host three times against a real temp workspace:

1. **Seed.** Create Vera (leader), Clark, Kakiko, and Phoenix with stored
   titles and roles, create a workspace whose `memberIDs` order differs from
   agent creation order, warm the group binding, and seed a stale v5
   `AGENTS.md` block plus a project-owned line.
2. **Upgrade shape.** Stop the host and remove only the persisted
   `nativeFirst` key from the isolated plugin store. The fixture reports row
   counts and the removed key only; it never reads or copies message content.
3. **Run.** Restart, assert the absent value resolved to `on` and was persisted,
   assert the generated v6 roster table, drive the leader turn, and exercise
   rollback and restore.
4. **Restart.** Restart again and assert durable turns, ledger, roster, and the
   no-completion result.

The explicit delegation uses the documented `:tools legacy` surface while
native-first stays `on`: the native tool list deliberately omits
`ensemble_delegate`, so the migration override is the only way one native turn
can call it. Native ingestion, routing, the contact ledger, and completion stay
on the native path.

## Review-fix pass

The two-axis review of the #241 cutover produced these code and harness fixes.
Behavior changes are covered by the unit/service suites; the live results below
were re-recorded on this branch.

- **One native-first default.** `DEFAULT_NATIVE_FIRST_MODE` is the single
  exported `on` constant used by `DEFAULT_SETTINGS`, `nativeFirstMode`, and the
  one-time store migration. An explicit persisted `off`/`shadow` is never
  rewritten; absent or invalid values migrate to the default.
- **Explicit-tool dedupe.** After the existing idempotency lookup, delegate,
  handoff, and group-post/approval paths check the native turn's `contacted`
  ledger. A recipient already contacted in the turn gets a clear
  "already contacted this turn" result and no second child or approval.
- **Anchor validation.** The pure anchor resolver now requires the candidate
  task to belong to the calling workspace and agent (including a workspace
  direct `dm:<agent>:<workspace>` turn). The group-channel rule that a
  workspace post must not borrow a DM turn remains a separate documented
  condition in `send_message`.
- **Anchor cleanup.** The unused `taskMaxHops` field was removed from
  `ActiveTurnAnchor`; the contact ledger remains and is the dedupe source.
- **Typed contact source.** `NativeContactSource` is a domain union; the
  durable ledger stores recipient IDs only and the source code stays in the
  `native.contact.recorded` log event.
- **One focus model.** Card focus registers every rendered card at successive
  `WORK_CARD_ROWS`, matching the renderer's `section.cards`; one-card
  pagination makes this a no-visual-change agreement.
- **One command catalog.** Command arity lives on `CommandSpec`; parsing and
  completions derive from `COMMANDS`. `:native-first on` changes only the mode
  and never clears an explicit `toolSurface: legacy`; `:tools native` is the
  separate restore.
- **Harness exactness.** The Vera driver imports the product
  `teamRosterTable` renderer (run with `--experimental-strip-types`) for the
  expected table, keeps an independent leader-first/memberIDs ordering
  assertion, and applies the real `nativeFirstCommand` / `toolsCommand`
  patches through `settings.update`. The TUI key handler is a thin wrapper
  covered by `src/v2/tui/commands.test.ts`.
- **Default-on service coverage.** A fresh store with no seeded settings
  starts `on`, persists the default, and registers the native surface.

The broad `test:live:fake` walkthrough predates default-on and asserts the
legacy direct, DM-queue, and statusline surfaces. It now runs that scenario on
the explicit legacy path; the Vera regression covers the default-on cutover,
and the unit/service suites cover the default itself. This keeps the legacy
assertions meaningful instead of rewriting them to the new surface.

The dispatch-budget probe inside `test:live:multilocation` also predates
default-on and drives the explicit `ensemble_handoff`/`ensemble_delegate`
tools, which the native surface deliberately does not register. It now pins
`nativeFirst: "off"` before each scenario and waits for the mode to land, so
the budget ledger is exercised on the legacy surface it was written for.

  removed key, and no `nativeFirst` key afterwards.
- After restart: the store contains `nativeFirst: "on"`, the diagnostic
  reports `on`, and `agent.sessionBinding` reports `mode: "on"`.
- The `native.mode` log reports `mode: "on"` and `migrated: true`.

**Generated roster table**

(fixture titles/roles; leader first and marked, then `memberIDs` order):

|---|---|---|

| Phoenix | Roster Keeper | Keeps the generated team roster exact. |

The expected table is the product `teamRosterTable` renderer's exact output
(imported by the driver under `--experimental-strip-types`), and a separate
assertion parses the rendered member names to prove leader-first then
`memberIDs` order. The project-owned line outside the Ensemble markers survives
and the stale v5 text is gone.

**Rollback and restore**

- `nativeFirst: "off"` plus `toolSurface: "legacy"` reports `off` and runs one
  non-native legacy task to `replied`; the provider request carries all 11
  legacy Ensemble tool schemas. The driver imports `nativeFirstCommand` and
  `toolsCommand`, validates each, and sends their patches through
  `settings.update`, so the live scenario exercises the same command catalog
  the TUI uses. The TUI key handler is a thin wrapper covered by
  `src/v2/tui/commands.test.ts` (#240).
- Every durable native turn, the parent result row, and the three-entry contact
  ledger survive the rollback.
- Restoring runs `nativeFirstCommand(["on"])` and `toolsCommand(["native"])`;
  the mode command alone never clears an explicit legacy surface. The restore
  reports `on` and keeps the same turns and ledger.
- After the second host restart: mode `on`, native sync `live`, parent phase
  `replied`, ledger unchanged, one successful execution event, one Phoenix work
  item, no completion task, no stuck turn, the exact roster table, one parent
  row, and one leader-authored row after the turn (the intentional legacy
  rollback row is excluded). Total work rows are unchanged.
